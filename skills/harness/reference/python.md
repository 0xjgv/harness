That is the complete working tree of `python/`, every file in exactly one
bucket. Three notes:

- **There is no KEEP bucket.** An earlier version of this manifest kept
  `tests/test_init.py`, `tests/features/smoke.feature` and
  `tests/features/steps/smoke_steps.py` as "scaffolding". They are not: all
  three `import src`, which the adopter does not have, and copying any

- `tests/test_properties.py` is the Hypothesis worked example the behavior
  contract's law-like rule points at. Read it before discarding it, then write
  the equivalent over the adopter's own law-like code.
- **If the repo already has a `harness.py`, diff it before overwriting.** Both
  test repos had forked the template months earlier and grown local features
  (doghouse: a Cursor Stop hook and a Django `makemigrations` gate; fusion: its
  own scoping implementation). Overwriting silently deletes those features, and
  any test that imports them breaks at collection time:
  `ImportError: cannot import name 'CURSOR_STOP_HOOK' from 'harness'`. Port the
  local features forward or delete their tests deliberately — never by surprise.

## 2. `harness.py` — the six module constants you must set

They sit together at the top of the file under `# ── Configuration ──`.
Setting them is the entire adaptation; nothing else in the runner is edited.

```python
APP_SOURCES  = ("src",)               # → the repo's real top-level packages
QUALITY_SOURCES = ("src", "harness.py")  # → (*APP_SOURCES, "harness.py")
TEST_DIR     = "tests"
TEST_COMMAND = ("-m", "unittest", "discover", "-s", TEST_DIR, "-q")
CLAUDE_STOP_COMMAND = "cd $CLAUDE_PROJECT_DIR && uv run harness stop-hook || exit 2"
CODEX_STOP_COMMAND  = '… .codex/hooks/codex-stop-hook.sh uv run harness stop-hook'
```

- **`TEST_COMMAND`** is the argv tail handed to the interpreter *and* to
  `coverage run`, so `test` and `coverage` can never drift apart. The template
  default is stdlib unittest. **Both real repos are pytest**; setting
  `("-m", "pytest", "-q")` is the one-line edit that makes a pytest suite run
  at all. Measured on doghouse: 735 passed with no `ImportError`, versus a
  collection-time abort before the edit.
- **`CLAUDE_STOP_COMMAND` / `CODEX_STOP_COMMAND` are the real knobs for the
  hook JSON.** Editing `.claude/settings.json` by hand does not survive:
  `setup-hooks` → `_install_stop_hook()` replaces any existing stop-hook
  handler with these constants. Measured: a hand-adapted
  `.venv/bin/python harness.py stop-hook` was silently reverted to
  `uv run harness stop-hook` by one `setup-hooks` run. Edit the constants, then
  run `setup-hooks`, then verify the JSON.
- The template's hooks say `uv run harness`, which needs a `[project.scripts]`
  console script. **A pip repo has none, so that command cannot work** — and
  `check`'s `✓ Stop hook wiring` will not tell you, because it only greps the
  file for the strings `Stop` and `stop-hook`. Run the command verbatim
  yourself once — §5 step 6 shows how.

## 3. Config vehicles — where the ruleset actually goes

This is the step an earlier manifest got wrong, and it is the one that decides
whether the harness produces 390 findings or 19,581 on the same repo.

**Never create a `pyproject.toml` that does not exist, and never add a
`[project]` table to one that lacks it.** Adding `[project]` to a
pip/`requirements.txt` repo changes how it builds and installs — a migration,
not a harness adoption, and not yours to make. But that rule is not a licence
to skip the ruleset: every tool the harness drives has a config file that is
not `pyproject.toml`. Use it.

| Tool | `[project]` in pyproject.toml | config-only pyproject.toml | no pyproject.toml |
|---|---|---|---|
| ruff | merge `[tool.ruff*]` | merge `[tool.ruff*]` | **`ruff.toml`** — same tables with the `tool.ruff` prefix dropped: `[tool.ruff.lint]` → `[lint]` |
| basedpyright | merge `[tool.basedpyright]` | merge | **`pyrightconfig.json`** |
| coverage | merge `[tool.coverage.*]` | merge | **`.coveragerc`** |
| dev deps | merge `[dependency-groups] dev` | do **not** add | do **not** add — install into the venv the repo already uses |

Measured: fusion has no `pyproject.toml` at all, and a `ruff.toml` carrying the
template's ruleset is picked up by both `ruff check` and `ruff format` — 3,228
findings over its app sources with the file present, 1,030 with `--isolated`.
That is what closes the "no `pyproject.toml` → never receives the ruleset" hole
that made the previous version of this manifest self-contradictory.

**If the repo already has a `[tool.ruff]`, keep theirs.** doghouse's is a
hand-tuned ~80-block `per-file-ignores` map over a legacy Django tree.
Overwriting it with the template's ruleset is what produces the headline
19,581-finding number (measured; keeping theirs gives 390); that figure is the
*cost of overwriting*, not a property of adoption. Union the `select` lists only
with the human's sign-off, one rule family at a time — and note that raising
`select` raises the whole-tree count but not the scoped one, so the pain arrives
later, on the first file anyone touches.

**But one merge is mandatory, not optional: the `"harness.py"` entry under
`[tool.ruff.lint.per-file-ignores]`.** Union the template's list into theirs.
The file you just copied in is *in scope on the first run* (§5), and it needs
its own exemptions or it fails the gate on itself. Measured on doghouse, whose
entry predated the template gaining two of them:

```
✗ Fix lint errors
Command failed: uv run --no-sync ruff check … harness.py
harness.py:1723:16: S314 Using `xml` to parse untrusted data …
```

The template's current list is `S404 S603 S607 S405 S314`. Adding the two
missing codes turned that gate green. Diff the two lists; do not assume an
existing entry is current.

**`.importlinter`**: do not copy it. Its `layers = adapters / core` contract
names the template's worked example. If the repo has a real layering, write it;
otherwise **delete the file** — `_arch_gates_or_warn()` prints
`⚠ Arch: no .importlinter — skipped` and passes. Measured on both repos.
(fusion has no `__init__.py` anywhere, so import-linter has no root package to
point at; deleting is the only correct answer there.)

**`Makefile`** is not verbatim: it hardcodes `HARNESS := uv run harness`. In a
pip repo that resolves to whatever `harness` is first on `PATH` — measured on
fusion, it found an **unrelated global `harness` binary from another project**
and produced plausible-looking output for the wrong repo. Set `HARNESS` to the
same prefix you use everywhere else (§4).

## 4. The invocation prefix, and the AGENTS.md hazards

### The prefix must name a real interpreter

`harness.py` uses `X | None` in a module-level type alias, so it needs Python
≥ 3.10 at import. The documented `python3 harness.py` picks up whatever
`python3` is first on `PATH`; on macOS that is the system 3.9:

```
File "harness.py", line 852, in <module>
    LineRanges = list[tuple[int, int]] | None
TypeError: unsupported operand type(s) for |: 'types.GenericAlias' and 'NoneType'
```

Use the project's own interpreter. The three prefixes seen in the wild:

| Repo shape | Prefix |
|---|---|
| uv project with `[project.scripts]` | `uv run harness <cmd>` |
| pip repo with a `.venv` | `.venv/bin/python harness.py <cmd>` |
| activated virtualenv | `python harness.py <cmd>` |

Use one prefix everywhere: `CLAUDE.md`, `Makefile`'s `HARNESS :=`, and the two
Stop-command constants in §2.

### AGENTS.md / CLAUDE.md

Byte-identical `AGENTS.md`/`CLAUDE.md` is a **packaging convention** — Claude
reads one, Codex the other — not a quality property. A repo with its own
hand-written `AGENTS.md` has two files that legitimately differ.

- **`HARNESS_ALLOW_AGENTS_MD_DRIFT=1` is the documented retrofit path**, not an
  escape hatch. Set it rather than reconciling two documents the harness has no
  business merging.
- **`sync-agents-md` refuses to clobber** a differently-cased twin (`agents.md`
  on APFS, where `Path("AGENTS.md").write_bytes()` writes straight *through* and
  `exists()` cannot see it), a symlink pointing anywhere but `CLAUDE.md`, or an
  `AGENTS.md` less than 50% line-similar to `CLAUDE.md`
  (`AGENTS_MD_SYNC_MIN_RATIO`). Before this refusal existed it destroyed 277
  lines of doghouse's `agents.md`.
- Both hazards are live, not hypothetical. Measured: **doghouse tracks
  `agents.md` (lowercase) and no `CLAUDE.md`**; **fusion tracks `CLAUDE.md` as a
  symlink to `AGENTS.md`** (`120000 … CLAUDE.md`), so appending to `CLAUDE.md`
  writes through to `AGENTS.md` and `git status` reports the *other* file
  modified. Run `ls -la CLAUDE.md AGENTS.md` before touching either — on
  doghouse, `ls -la agents.md AGENTS.md` lists **two names, one inode, one
  size**, which is the whole hazard in one line of output.
- Expect this gate to be red on the first brownfield `check`, and expect that.
  Measured on doghouse: `✗ agents-md-drift: AGENTS.md differs from CLAUDE.md
  (first diff at line 1)`. The fix is
  `HARNESS_ALLOW_AGENTS_MD_DRIFT=1`, which prints
  `⚠ agents-md-drift: skipped` — not `sync-agents-md`, which would be the data
  loss the refusal exists to prevent.

## 5. First run — seven steps, in this order

```bash
H=".venv/bin/python harness.py"     # or: uv run harness — see §4

$H suppressions --update-baseline   # 1. snapshot every metric as it is today
$H check                            # 2. expect red the first time; fix, re-run
git add -A && git commit            # 3. THE HUMAN commits the adoption (see below)
$H setup-hooks                      # 4. installs git hooks + rewrites hook JSON from §2
grep -o '"command": "[^"]*"' .claude/settings.json   # 5. verify the prefix survived
sh -c 'cd . && .venv/bin/python harness.py stop-hook || exit 2'   # 6. the hook, verbatim
$H check                            # 7. green, from a clean tree
```

Steps 5 and 6 are not ceremony. Step 4 rewrites the hook JSON from constants
inside `harness.py`, and the `✓ Stop hook wiring` gate cannot tell a working
command from a broken one — those two lines are the only thing that can.

### Step 1 fails loudly, and that is correct

`--update-baseline` is **all-or-nothing**. Three outcomes per metric:

- **measured** → written, possibly `0`;
- **not applicable** → the key is *removed* from the file. Absence on disk
  means report-only. This removal is what stops the template's shipped
  `coverage.min 100` from being inherited by a repo that has no tests;
- **could not measure** → nothing is written at all, and the failing metric is
  named. Measured on doghouse:

```
✗ .harness-baseline not written — could not measure:
    coverage.min: the test run under coverage failed (exit 2)
  ↳ fix: make the measurement pass, then rerun `suppressions --update-baseline`
```

That is the runner telling you `TEST_COMMAND` (§2) is still wrong. Fix it and
rerun; do not hand-write the file.

### Step 2 is not "green by construction"

The previous manifest claimed it was. It is not, and the difference matters.
The adoption itself modifies `harness.py`, `CLAUDE.md`, `.gitignore`,
`vulture_allowlist.py` and the config files — and `harness.py` is inside
`QUALITY_SOURCES`, so **the first-run scope is never empty**. `fix`, `format`,
`lint` and `typecheck` all run, against the adopter's ruleset, over the file
you just copied in.

Measured, both directions. On fusion (ruleset supplied fresh via `ruff.toml`) it
passed first time. On doghouse (ruleset already present and slightly stale) the
**first `check` was red on exactly two gates, both of them the harness's own
files**:

```
✗ Fix lint errors        harness.py:1723:16: S314 …   → §3, union the per-file-ignores
✗ agents-md-drift        AGENTS.md differs …          → §4, HARNESS_ALLOW_AGENTS_MD_DRIFT=1
FAIL 9 passed, 2 failed (1893.8s)
```

Neither is a code-quality finding about the repo; both are adoption wiring. Both
have a one-line fix given above. **Expect them, fix them, re-run** — and do not
report a green you did not see. The failure summary counts one result per gate,
so the `2 failed` always equals the number of `✗` lines above it.

### Step 3 is the human's, and it is not optional

Until the adoption is committed, every subsequent `check` re-scopes over the
whole adoption diff. The behavior contract forbids the agent from committing
(`Do NOT run git commit … unless the user's current prompt asked for it`), so
**say this out loud and hand it back**: *"the adoption is staged; commit it
before the gates mean anything."* An agent that skips this and reports green has
reported a green over its own uncommitted diff.

### What makes step 2 green on a 208k-line repo

Two mechanisms, and between them every gate is covered:

- `fix`, `format`, `lint`, `typecheck` are **diff-scoped**, and scoped to
  changed *lines*, not whole files (see `python/CLAUDE.md` `## Scoping`). They
  skip with a warning on an empty scope and never widen to the whole tree.
- `coverage`, `complexity`, `crap`, `deadcode`, `suppressions` are
  **count-ratcheted** and stay whole-tree — scoping a count makes it
  meaningless. Step 1 wrote each floor at the number the repo already has.

Nothing asks the repo to be better than it is; it asks the *change* to be no
worse. Then hand the crank to `/ratchet` (`skills/ratchet/`), which raises the
floors by adding tests only.

## 6. CI

`.github/workflows/ci.yml`: keep their job matrix, and replace the harness step
with `<prefix> ci`. "Merge only the `harness ci` step" is not enough guidance —
fusion's existing step was `python3 harness.py ci --no-test`, and **`--no-test`
is not a flag this runner implements**. Unknown flags are parsed as positional
argv and silently ignored, so the step ran the *full* `ci`, including tests, and
nobody noticed. Audit the existing step's flags against `TASKS` in `harness.py`
before keeping any of them.

Two CI-specific requirements:

- **`fetch-depth: 0`**, or pass `--base=<ref>`. An unresolvable *fallback* base
  (shallow clone, no `origin/main`) leaves the scope empty and the scoped gates
  **skip green** — a gate that verified nothing. An unresolvable *requested*
  base (`--base=<ref>`, `HARNESS_ARCH_BASE`, `GITHUB_BASE_REF`) is treated as a
  typo instead: `check`/`stop-hook` warn, `pre-push`/`ci` **fail**. Note the
  literal spelling: `--base=<ref>`. A bare `--base=` is an empty string, falsy,
  and a no-op.
- **`uv sync` / `pip install` before `ci`.** `audit` requires a *pre-existing*
  `.venv` and warns-and-skips otherwise, precisely so `ci` never creates one.
  The cost, stated plainly: a dependency bumped in `pyproject.toml` but never
  installed goes unaudited.

## Tool resolution (`_tool`)

Three tiers, in descending order of fidelity:

1. **`uv run <tool>`** — when `.venv/bin/<tool>` already exists **and**
   `pyproject.toml` exists (`--no-sync` added for read-only gates).
2. **`.venv/bin/<tool>`** — when the binary exists but there is no
   `pyproject.toml`: a pip-installed virtualenv, not a uv project.
3. **`uvx <tool>`** — whenever `.venv/bin/<tool>` does not exist.

Tier 1 is gated on the **binary already existing**, not on `pyproject.toml`
alone: `uv run` on a missing tool does not fall through — it exits 2 with
`Failed to spawn` and *creates* `.venv` on the way, which a read-only gate must
never do. That gate is also what keeps `uvx` reachable in a config-only
`pyproject.toml`.

Two measured details:

- Tier 3 resolves a **distribution** name, so a tool whose console script
  differs needs `--from`: `uvx --from import-linter lint-imports`
  (`TOOL_DISTRIBUTIONS` in `harness.py`).
- **Install `coverage` into the project's own venv.** If it falls through to
  `uvx coverage`, the isolated environment has no pytest and `coverage run -m
  pytest` dies. The same applies to `lint-imports` when the repo has a real
  `.importlinter`.
- In a config-only `pyproject.toml` repo, tier 1 works and uses the existing
  `.venv`; a non-read-only `uv run` additionally writes an untracked `uv.lock`.
  Add it to `.gitignore` or commit it deliberately. (It does **not** wipe the
  pip-installed environment — an earlier draft of this file claimed it did, from
  an install that had failed for an unrelated reason. It does not.)

## `.harness-baseline` — six metrics, one writer

```
complexity.max_violations 0
coverage.min 100
crap.max_violations 0
deadcode.max_findings 0
duplication.max_blocks 8
suppressions.noqa 8
suppressions.pyright_ignore 2
suppressions.type_ignore 4
```

- **Six**, not four. `deadcode.max_findings` was added because vulture
  produced 1,583 findings on doghouse with no floor and no escape.
  `duplication.max_blocks` was added because the complexity gate scores each
  function alone and never sees the same block written twice.
- **`duplication.max_blocks` is lizard's `-Eduplicate` block count** — a second
  lizard invocation over the *same* targets as the complexity gate
  (`src` + `tests`), run `-w -i 1000000` so lizard stays quiet and green while
  the runner counts lines equal to `Duplicate block:` and judges them itself
  (lizard's exit code tracks CCN warnings only, never duplicates). Change the
  target set and the recorded floor stops reproducing. Overlapping near-
  duplicates are reported as separate blocks, so the count can move by one on a
  trivial edit — harmless for a ratchet, which only asks that it never grow.
  The template ships `8`, all of them in `tests/` where repeated setup is the
  readable choice; a fresh adopter's step 1 overwrites it, same as
  `coverage.min`.
- **The only writer is `suppressions --update-baseline`.** Nobody guesses that
  from the name — say it out loud when handing the repo over. The name is a
  known wart, deliberately unfixed: `suppressions` sits in the parity gate's
  non-allowlistable `CORE_COMMANDS`, so a `baseline` command would have to land
  in all four templates. Deferred to the bun/go/rust port.
- **A missing `.harness-baseline` is report-only and passes** — verified for
  every metric, complexity included:
  `✓ Complexity (lizard, report-only: no .harness-baseline floor)`,
  `⚠ Dead code (vulture): 177 finding(s), report-only (no .harness-baseline floor)`,
  `✓ Duplication (lizard): 8 block(s), report-only (no .harness-baseline floor)`.
- `coverage.min` is the floor. `[tool.coverage.report] fail_under` is **not**
  read — the harness always passes an explicit `--fail-under=<n>` on the CLI.
- **`coverage.min 100` ships in the committed template baseline.** Greenfield
  inherits it; brownfield never does, because step 1 re-baselines first. Tell
  the adopter the `100` they see in the freshly copied file is about to be
  overwritten, not a target.
- Unrecognised keys are preserved across an update.

## Why this design, in measured numbers

Three real repos, first-party Python only:

| | doghouse | fusion |
|---|---|---|
| Package manager | pip + requirements.txt | pip + requirements.txt |
| `pyproject.toml` | config-only, no `[project]` | **none at all** |
| Python LOC | 208,113 | ~62,600 |
| Ruff, **template ruleset replacing theirs** | **19,581** | 3,769 |

Ruff counts are `ruff check --no-fix` over the whole repo, ruff 0.16.0. The
bolded floors are the numbers `suppressions --update-baseline` actually wrote.
The doghouse pair is the point: **19,581 findings if you overwrite their
`[tool.ruff]`, 390 if you keep it.** That factor of fifty is a merge decision,
not a property of the harness.

A whole-tree strict gate on doghouse is ~30,000 findings on day one. Nobody
fixes that, so the harness gets deleted instead of adopted. Both doghouse and
fusion had independently forked this template and hand-added diff-scoping before
it shipped here; fusion's runner docstring reads *"Scoping rule: fix/format/lint
NEVER run against the whole tree… Adopting the harness must not rewrite or fail
on fusion's pre-existing code."* Two independent adoptions invented the same
missing feature. Do not "helpfully" widen the scoped gates during a port.

The trade-off, stated plainly so the adopter accepts it knowingly: **a green
scoped run is not a clean repo.** A pre-existing violation on a line the change
does not write is not reported, and the tree is never fully clean — only clean
at the boundary of what changed.

### Two scoping rules an adopter will otherwise mistake for bugs

- **`I001` is deliberately not in `WHOLE_FILE_CODES`** (which holds only `F401`
  and `F811`). Ruff reports an unsorted import block spanning the whole block,
  so an edit inside the imports already intersects it under the ordinary line
  filter. Exempting it too would turn a pre-existing unsorted block red the
  moment you append a comment elsewhere in the file — with no way out, because
  `fix` cannot resort a block without rewriting untouched lines. The gate would
  be red with no exit. The reasoning is a code comment and is pinned by a test.
- **`fix` has a weaker guarantee than `lint`.** `ruff check --fix` rewrites a
  whole file or nothing, so `fix` runs it and then **restores the file
  byte-for-byte if the rewrite touched any line this change did not write**,
  printing `⚠ Fix: reverted N file(s)…`. It is all-or-nothing per file, never
  partial. The cost: in a file that also needs an off-scope fix, an *in-scope*
  auto-fixable finding is not auto-fixed either — lint reports it for a human.
  `fix` promises *"never rewrites a line you did not touch"*, **not** *"always
  fixes what it could"*. Say this plainly or the adopter concludes `fix` is
  broken.

### Python-only, for now

`--whole-file` and line-level (as opposed to file-level) scoping exist **only
in the Python runner**. `bun/harness.ts`, `go/harness.go` and `rust/harness.rs`
have no equivalent — measured: zero occurrences of `whole-file` in all three.
`scripts/parity-gate.sh` passes anyway because it compares *subcommands*, not
flags. This is a deliberate scope boundary while Python is the reference
implementation, and a real divergence to close during the port. Recorded here so
it is found on purpose rather than discovered by accident.

## Known limitations

- **`test` is the one gate with no adoption ramp.** `check` runs `TEST_COMMAND`
  whole and unratcheted: if the suite is red in the environment where `check`
  runs, `check` is red, and no baseline or scoping rescues it. A repo whose
  suite needs a database, a service, or an API key must have it present.
  Measured on fusion: `LLM_API_KEY` unset → 55 collection errors → red `check`;
  set to any string → 1042 passed → green. Set `TEST_COMMAND` to the invocation
  that genuinely passes in that environment, and tell the human what it needs.
  The same on doghouse, in numbers: with no database, **735 passed, 1 skipped,
  2,980 errors**; with one, **3,711 passed, 2 failed**; with the two
  network-dependent tests deselected, green. Note what the deselection *is* — a
  deliberate, commented narrowing of `TEST_COMMAND` to what the environment can
  run, not a weakened gate. Write the comment.
- **`--update-baseline` runs the suite up to three times** (coverage, then CRAP
  re-runs it). On fusion's 75-second suite that is a four-minute step; on
  doghouse's 32-minute suite it is an hour and a half. Run it in the background.
- **The `✓ Stop hook wiring` gate cannot verify the hook works** — it only greps
  the settings file for `Stop` and `stop-hook`, so it is green on a command that
  cannot execute. Run the command verbatim once yourself (§5 step 6). Verified
  by doing exactly that: `stop-hook exit=0`, five gates printed.
- **`git status` is not a reliable adoption checklist when `CLAUDE.md` is a
  symlink.** On fusion, appending to `CLAUDE.md` showed up as `M AGENTS.md` and
  `CLAUDE.md` unchanged. Read the modes (`git ls-files -s`), not the names.

## CLAUDE.md

`AGENTS.md` and `CLAUDE.md` in the template hold the same content
byte-for-byte. Copy `~/Code/harness-templates/python/CLAUDE.md` verbatim and
rewrite only the invocation prefix (§4); do not paraphrase — it drifts, and the
file is the contract an agent actually reads. Four sections: `## Commands`,
`## Scoping`, `## Definition of done`, `## Behavior contract` (Layer 2, see
[behavior-contract.md](behavior-contract.md)). That file is the authority on
exact per-command semantics; this one is the authority on getting them into a
repo that did not have them.
