# CLAUDE

## Commands

- After edits: `uv run harness check` — lockfile check (`uv lock --check`, warns and skips with no `uv.lock`), fix, format, typecheck **on changed files only** and test **on the modules those files map to** (see Scoping; syntax check when no tests exist); then, read-only, complexity + duplication + acceptance run as a parallel batch, then the count-ratcheted gates deadcode and arch (import-linter), then the two **delta** gates the stop hook runs (complexity delta, dead-code delta — see Delta gates), followed by the arch config guard (warn), the gherkin-first guard (warn), agents-md drift, and the suppression ratchet. **Invariant: `check` runs every gate that is offline, fast, and takes no build lock.** Arch (import-linter) qualifies — it's a local dev dependency, runs offline, and takes no build lock — so it runs here too, just outside the batch: it compares a count to a baseline floor rather than an exit code. `ci` adds only: the dependency audit (network), coverage, CRAP (advisory), and mutation (advisory, scoped to the change). Every step accumulates instead of failing fast, so one run surfaces every problem, and it ends with an `OK N passed (Xs)` / `FAIL N passed, M failed (Xs)` summary line that counts one result per gate — the `M` always equals the number of ✗ lines above it.
- Pre-commit: `uv run harness pre-commit` — the arch config guard and the gherkin-first guard run first, staged-mode, before checking whether any Python files are staged, so a commit that stages only an arch config edit (or any other non-Python file) still gets blocked. Only then: staged Python files (auto via git hook) get fix/format, which rewrite the working tree, then the fixed files are re-staged (`git add`) so the commit records the fixed content. Caveat: if a file is only partially staged, `git add` also stages its unstaged hunks — the same trade-off lint-staged makes.
- Pre-push: `uv run harness pre-push` — read-only push gate: lint + format check on the changed set (see Scoping), acceptance over the whole tree in parallel, then arch (the offline checks pre-commit and stop-hook skip). Auto via git pre-push hook.
- CI: `uv run harness ci` — read-only gates (lint, format check, typecheck — changed set; audit, complexity, duplication, acceptance — whole tree) run in parallel — captured, printed in submission order, run to completion — then the count-ratcheted deadcode and arch, then coverage (streams) + crap + mutation. CRAP and mutation are advisory (warn only — pass `--enforce` to hard-fail both). `.github/workflows/ci.yml` pins `uv` (`setup-uv` `version:`) and Python (`python-version:`, the `requires-python` floor; it sets `UV_PYTHON`, which `uv python install` and `uv sync` both honor) so the remote gate resolves the same toolchain as the lock instead of whatever the runner image ships that week.
- Complexity: `uv run harness complexity` — lizard (pinned dev dependency, resolved via `uv run`/`.venv`/`uvx` fallback — see Scoping) CC gate (CCN≤15, args≤8, length≤100) over src + tests, plus a second lizard run with `-Eduplicate` over the same targets that counts `Duplicate block:` headers against `duplication.max_blocks` in `.harness-baseline`. Both are count-ratcheted: report-only until `suppressions --update-baseline` records the floor, then the number may only move down. lizard's exit code ignores `-Eduplicate`, so the harness judges the block count itself; the two runs share one parallel batch in `complexity`, `check` and `ci`. The stop hook keeps duplication but swaps the whole-tree complexity gate for the delta form (see Delta gates).
- Deadcode: `uv run harness deadcode` — vulture (pinned dev dependency, same resolution) over `src/` only (`--min-confidence 60`); a dead helper that still has a test surfaces rather than hides. Allowlist dynamic references (decorator handlers, getattr) in `vulture_allowlist.py`. Runs whole-tree in check + ci; the stop hook runs the delta form instead (see Delta gates).
- Audit: `uv run harness audit` — audit dependencies for known vulnerabilities (via pip-audit) against the **already-installed** `.venv`. Warns and skips when there is no `.venv`, and passes `--no-sync`, because `ci`/`pre-push` must not create or mutate an environment — measured: `--no-sync` alone does *not* stop `uv run` from creating a missing `.venv`, so the presence check is the load-bearing half. The cost, stated plainly: a dependency bumped in `pyproject.toml` but never installed goes unaudited. Run `uv sync` first (CI does).
- Acceptance: `uv run harness acceptance` — run behave against `tests/features/`
- Test: `uv run harness test` — runs the test modules that map to the changed files (see Scoping); `--all` runs the whole suite. The suite itself is `TEST_COMMAND`, the module-level constant in `harness.py` next to `APP_SOURCES`/`TEST_DIR`. Default is stdlib unittest (`("-m", "unittest", "discover", "-s", TEST_DIR, "-q")`); a pytest repo edits that one line to `("-m", "pytest", "-q")` and nothing else — the coverage run reads the same constant, so `test` and `coverage` can never drift apart. Falls back to a `py_compile` syntax check when no `tests/test*.py` exist. The interpreter and coverage are resolved through the same tiers as every other tool (see Scoping), so a pip repo runs against its own `.venv`, not a fresh one.
- Coverage: `uv run harness coverage --min=0` — coverage.py with threshold + uncovered listing; the real default knob is `coverage.min` in `.harness-baseline` (`[tool.coverage.report] fail_under` in `pyproject.toml` is not read — the harness always passes an explicit `--fail-under=<n>` on the CLI, which wins); warns and skips when no `tests/test*.py` files exist; a non-integer `--min=` value prints an error and exits 1
- Mutation (advisory): `uv run harness mutation` — mutmut over the app sources this change touched (`--all` for the whole tree), scored as `round(100 × (killed + timeout) / (killed + timeout + survived + suspicious))`; mutants that never ran (`no_tests`, `skipped`) are excluded from both sides. Compared to `mutation.min` in `.harness-baseline`, report-only when that key is absent, advisory otherwise (green ⚠, exit 0) — `--enforce` turns a miss into a red ✗ and exit 1. Runs in `ci`, after CRAP, where it never fails the build unless `ci` itself was invoked with `--enforce` (the same argv-driven rule CRAP already follows). Skips with a warning when the change touched no app source, when there are no `tests/test*.py` files, and when `.venv/bin/mutmut` is missing — mutmut imports the project's own modules and test suite, so unlike every other tool here it has no `uvx` fallback. Config lives in `[tool.mutmut]`. **`mutants/` belongs to mutmut**, which hardcodes that path: the gate deletes it before each run (mutmut keeps every previous verdict there, and a scoped run layered on a differently scoped one would score files the change never touched) and again after (the copy contains `mutants/tests/`, which makes a pytest suite abort collection on duplicate module names). A `mutants/` directory that git *tracks* is treated as yours and the gate refuses rather than deleting it.
- CRAP (advisory): `uv run harness crap --max=30` — complexity × coverage gate. Add `--enforce` to exit 1 on offenders (default exits 0 with warning; prints a green ⚠, not a red ✗ — ✗ is reserved for `--enforce` runs that actually fail). Warns and skips when no tests exist.
- Suppressions: `uv run harness suppressions` — full suppression breakdown; `--update-baseline` requires human sign-off and updates `.harness-baseline`. It is all-or-nothing: every floor it can measure is rewritten, a floor it cannot measure is dropped, and a measurement that *failed* aborts the write entirely. `mutation.min` is the one key it does not measure by default — a whole-tree mutmut run costs minutes — so it is carried through untouched unless you add `--with-mutation`.
- Arch: `uv run harness arch` — import-linter against `.importlinter`, ratcheted by `arch.max_violations` in `.harness-baseline`: the number of broken import chains may never exceed the recorded floor, and a run below it suggests `--update-baseline`. **Report-only until a floor is recorded** — a real layering contract written over an existing tree breaks in dozens of places on day one, and the floor's job is to stop the 41st violation, not to demand the first 40 be fixed before the harness is allowed in. Warns and skips with no `.importlinter`; a run that produced no `Contracts: N kept, M broken.` summary is a tool failure, not a count of zero, and fails.
- Arch config guard: `uv run harness arch-config-guard` — blocks unreviewed `.importlinter` changes in pre-commit/pre-push/CI; use `HARNESS_ALLOW_ARCH_CONFIG=1` after review. Base ref for the diff is the shared one described under Scoping (`--base=` → `HARNESS_ARCH_BASE` → `GITHUB_BASE_REF` → `origin/HEAD`/`origin/main`/`main`) — so a direct push to `main` (no PR event) still gets checked; silently skipped if none of those resolve.
- Gherkin-first guard: `uv run harness gherkin-guard` — blocks a changed production-source file (`src/`, deliberately excluding `harness.py` and `tests/`) with no changed `.feature` file, in pre-commit (staged)/pre-push (incl. pre-push stdin refs)/CI; `check`/`stop-hook` only warn. Use `HARNESS_ALLOW_NO_FEATURE=1` after review to override. Passes silently when the template has no `.feature` files anywhere under `tests/features/` yet — adopting the harness into a repo with no acceptance suite never blocks.
- Agents drift: `uv run harness agents-md-drift` — fail if AGENTS.md differs from CLAUDE.md. Opt out with `HARNESS_ALLOW_AGENTS_MD_DRIFT=1`: byte-identical agent instructions are the right default *for this template* (one document, two filenames — Claude reads one, Codex the other), but not for a repo that already had a hand-written AGENTS.md before the harness arrived. There the two files legitimately say different things, and welding them together is not a quality gate — it is a merge the harness picked on the human's behalf. **Retrofit into a repo with its own AGENTS.md should set this env var, not reconcile.** Same accommodation `gherkin-guard` makes for a repo with no `.feature` files, for the same adoption reason.
- Sync: `uv run harness sync-agents-md` — overwrite AGENTS.md from CLAUDE.md, **refusing when that would destroy work**: a differently-cased twin (`agents.md` on a case-insensitive filesystem, where `write_bytes` writes straight through and `exists()` cannot tell), a symlink pointing somewhere other than CLAUDE.md, or an AGENTS.md less than 50% line-similar to CLAUDE.md (`AGENTS_MD_SYNC_MIN_RATIO`) — i.e. somebody's own document rather than a stale copy. A symlinked pair that already resolves to one file reports "nothing to do" and leaves the link alone. This matters because the drift failure is *guaranteed* on a brownfield adoption — the adopter has their own AGENTS.md and the template just dropped its CLAUDE.md beside it — so an unconditional copy would make data loss the default path through the harness.
- Setup: `uv run harness setup-hooks` installs git pre-commit + pre-push hooks (path resolved via `git rev-parse`, worktree-safe) and idempotently installs the Claude/Codex Stop wiring plus Claude's `PostToolUse` (`Edit|Write`) wiring; re-running replaces each handler in place rather than appending a second copy
- Post-edit: `uv run harness post-edit` — fix + format every file with uncommitted changes; the stop hook's mutating first step. Its `ruff check --fix` result is now *judged*, not just run: a violation left on a line this change wrote fails the stop hook under the gate name `Lint` (line-scoped, the same policy as `harness lint`, so a legacy violation on an untouched line stays out of it).
- Post-edit hook: `uv run harness post-edit --hook` — the `PostToolUse(Edit|Write)` entry point. Reads Claude Code's hook event on stdin, takes `tool_input.file_path`, and — only when that is a project `.py` file inside this template — fixes and formats that one file. Anything else (another subproject's file, a non-Python file, unparsable stdin) is a silent no-op. Fix and format are **line-scoped, exactly like `harness fix`/`format`** (see Scoping): a `ruff check --fix` that reaches a line this change did not write is reverted byte-for-byte, and `ruff format --range` runs per changed range — a file with no base version (untracked, or added since the base ref) is new in its entirety, so there the whole file is in scope. It always exits 0 and speaks through one compact JSON object on stdout: nothing when the file did not change, `hookSpecificOutput.additionalContext` telling the agent to re-read the file when formatting rewrote it, `{"decision":"block","reason":…}` carrying the line-scoped violations ruff could not fix. A block and a reformat cannot both be reported — block wins.
- Stop hook: `uv run harness stop-hook` — post-edit (fix + format, judged), arch config guard (warn), gherkin-first guard (warn), the **complexity delta** gate, the duplication gate, the **dead-code delta** gate. On failure it exits **2** and writes `stop-hook failed: <gate names>` to stderr followed by up to 20 finding lines (`<path>:<line>: <message>`) and, when truncated, one `… +N more` line. Claude Code treats exit 2 as blocking and feeds **stderr** back to the model (any other exit code is silently swallowed), so the findings have to be on stderr or the model never sees them — the human-readable ✓/✗ lines and full tool output stay on stdout. Codex's wrapper already turns any non-zero exit into a block.

## Scoping

`fix`, `format`, `lint`, `typecheck`, `test`, and `mutation` never run against the whole tree by default. They resolve one git-derived file list — working tree + index + untracked files + the diff against the base ref — and skip with a warning when it is empty. (`mutation` scopes to the app sources in that list, and by file, not by line — a mutant is a whole function.) Every other gate (`complexity`, `deadcode`, `coverage`, `crap`, `suppressions`, `acceptance`, `arch`) stays whole-tree.

Scoping is **line-level, not just file-level**. Within each scoped file, only the post-image line ranges this change wrote are in play, parsed from `git diff --unified=0`'s `@@` headers. Touching one line of a legacy module must not surface every violation already sitting in it — file-level scoping alone does exactly that, and it is what makes adoption fail on day two instead of day one.

- **Lint** (`ruff check --output-format=json --no-fix --force-exclude`) keeps only findings that intersect a changed range. The gate's label carries the arithmetic when it filtered anything: `Lint check (0/12 on changed lines)`.
- **Whole-file codes.** `F401` and `F811` are exempt from the line filter and reported anywhere in a scoped file: an import your edit orphaned and a definition it shadowed are real consequences of the change, reported on a line the change never wrote. `I001` is deliberately *not* exempt — ruff reports an unsorted import block spanning the whole block, so an edit inside the imports already intersects it normally; exempting it too would turn a pre-existing unsorted block red the moment you append a comment elsewhere, with no way out, because `fix` cannot resort it without rewriting untouched lines. `WHOLE_FILE_CODES` in `harness.py` is the list; extend it only on a concrete false negative, because every addition costs adoptability.
- **Format** scopes exactly — `ruff format --range=<start>-<end>` is native, so there is no approximation and no residue.
- **Typecheck** filters basedpyright's `--outputjson` diagnostics the same way (its lines are 0-based; the hunk ranges are 1-based). There is no type-level analogue of `WHOLE_FILE_CODES`.
- **Fix is weaker than lint, on purpose.** `ruff check --fix` rewrites a whole file or nothing — it has no line-range mode. So `fix` runs it, then compares the file to its pre-fix content and **restores the file byte-for-byte if the fix reached any line this change did not write**, warning `Fix: reverted N file(s)…`. It is all-or-nothing per file, never partial: accepting half a rewrite (a usage rewritten but its new import rejected) would produce code that does not run. The cost is real and worth stating: in a file that also needs an off-scope fix, an *in-scope* auto-fixable finding is not auto-fixed either — it is reported by the lint filter for a human to fix by hand. `fix` guarantees "never rewrites a line you did not touch", not "always fixes what it could".
- A file with no base version (untracked, or added on this branch) is entirely in scope — every line is new. A file that changed only by deletion has nothing in scope on the post-image; only whole-file codes can still fire.
- **Test** scoping is file-level, not line-level: a changed `tests/**/test*.py` runs itself, and a changed source module runs every `tests/**/test_<stem>.py` and `tests/**/test_<stem>_*.py` for its bare module name and its package path folded with underscores (`src/core/pricing.py` → `pricing`, `core_pricing`). The gate's label carries the arithmetic: `Tests (2/7 test modules)`. A changed source file that maps to no test gets one ⚠ line and is not a failure — the tests that do map still run. When only unmapped files changed, the gate skips; it never widens. Modules are named dotted (`python -m unittest -q tests.test_core_pricing`), which needs an `__init__.py` in every package on the way to each module; without one the gate warns and runs the whole suite, because `unittest discover -p` takes a single pattern and cannot scope. A non-unittest `TEST_COMMAND` (pytest) gets file paths appended instead. Only `check` and `pre-commit` scope the test gate: `ci` runs the whole suite through `coverage`, and `pre-push` runs no test gate at all.
- `--whole-file` keeps the changed-file scope but drops the line filter. Reach for it as a regression sweep over the files you touched.
- `--all` widens the scoped gates to the whole tree. Use it for a deliberate audit, or in a repo already at parity.
- `--base=<ref>` overrides the diff base for every changed-path consumer at once — the scoped gates, the arch config guard, and the gherkin-first guard. Precedence: `--base=` → `HARNESS_ARCH_BASE` → `GITHUB_BASE_REF` (pull_request events only) → the first of `origin/HEAD` / `origin/main` / `main` that resolves.
- `--verbose` streams each command's output live and echoes its argv as `-> <argv>`, and still prints the per-gate ✓/✗ line — the flag you reach for when something is wrong must not hide which gate failed.
- Tool resolution: `uv run` when `pyproject.toml` exists **and** `.venv/bin/<tool>` is already installed — with `--no-sync` for read-only gates, so `pre-push`/`ci` cannot install packages mid-gate — else `.venv/bin/<tool>`, else `uvx --from <dist>==<version> <tool>` pinned to the version `uv.lock` records for the tool's distribution (`_lock_versions`; the lock is the only place exact versions live, `pyproject.toml` holds ranges), so the fallback runs the same release `uv run` would have. No lock, unreadable lock, or no entry for the tool → plain `uvx <tool>`, unpinned; the pin is a fidelity gain, never a failure. Tier 1 is gated on the binary already existing because `uv run` on a missing tool does not fall through: it exits 2 with `Failed to spawn`, and it creates `.venv` on the way there, which a read-only gate must never do. So a `pyproject.toml` with no `[project]` table (the shape `uv sync` cannot install dev dependencies into) resolves through to `uvx` instead of failing forever. A repo with neither `pyproject.toml` nor `uv.lock` still runs.

**The trade-off, stated plainly.** Whole-tree absolute-threshold gates make adoption impossible for a large existing repo: this template's strict ruleset produces ~19,300 ruff findings on a 208k-line Django codebase and ~7,300 on a 62k-line one. Day one is a red gate nobody can fix, so the harness gets deleted instead of adopted. Scoping trades completeness for adoptability — a pre-existing violation on a line your change does not write is not reported, and the tree is never *fully* clean, only clean at the boundary of what changed. Two consequences to accept knowingly:

- **A green scoped run is not a clean repo.** Run `--whole-file` (same files, every line) or `--all` on purpose (a cleanup branch, a scheduled audit) to see the real number. The count-ratcheted gates — complexity, duplication, CRAP, coverage, dead code, arch, suppressions — stay whole-tree precisely so the totals can only move down. `mutation` is the exception that proves it: one whole-tree run costs minutes, so the gate is scoped while its `mutation.min` floor is measured whole-tree by `suppressions --update-baseline --with-mutation`. Floor and reading therefore answer different questions, which is why a miss only warns.
- **An unresolvable *fallback* base scopes to nothing, and passes.** In a shallow or detached checkout with no `origin/main`, the base diff is empty and the scoped gates skip rather than fail — the same silent skip the arch config guard already documents. Use `fetch-depth: 0` or pass `--base=` in CI so the scope is real.
- **An unresolvable *requested* base is an error, not a skip.** A base someone asked for explicitly (`--base=`, `HARNESS_ARCH_BASE`, `GITHUB_BASE_REF`) that git cannot resolve is a typo, and scoping to zero files because of it is a green gate that verified nothing. Each scoped gate then names the bad ref in its skip line instead of the generic "no changed Python files", `check`/`stop-hook` warn, and `pre-push`/`ci` fail. The fallback chain is untouched, so adoption into a shallow clone stays green.

## Delta gates

Two gates in `stop-hook` answer a different question from their whole-tree twins:
not "how much complexity/dead code does this repository carry" but "did this change
introduce or worsen any". A Stop hook fires after every agent turn, so the whole-tree
form hands the model the same pre-existing lizard table every time and asks it to fix
code the change never touched — the file-level version of the adoption failure line
scoping already exists to prevent. `check` and `ci` still run the whole-tree,
count-ratcheted pair; the delta pair runs in `check` too, so a green `stop-hook`
predicts a green `check`.

- **Complexity delta** (`Complexity delta (lizard)`) scopes to the same git-derived
  file list as `harness lint` (working tree + index + untracked + diff vs the base
  ref). For each changed project `.py` file it runs `lizard --csv` twice: once on the
  working-tree file, once on that file's content at the **merge base** of the diff
  base and `HEAD` (`git show <merge-base>:<path>`, written to a temp tree because
  lizard measures files, not strings; `HEAD` when no base ref resolves; nothing at
  all for a file that did not exist there). A function is reported only when it
  exceeds a limit **now** (CCN > 15, args > 8, length > 100 — the same constants the
  whole-tree gate passes lizard) **and** it is new or worse than the base version on
  that same metric. Functions are matched by lizard's `long_name` — the signature —
  so a function that only moved down the file is not "new". One line per offending
  metric: `<path>:<line>: <name> CCN <base>→<now> (limit 15)`, with `new` in place of
  `<base>` for a function this change introduced.
- **Dead-code delta** (`Dead code delta (vulture)`) runs vulture whole-tree exactly as
  today — what makes code dead is the *absence* of a reference anywhere, so the
  measurement cannot be scoped — and filters its output: a finding survives only when
  its path is a changed file and its line falls inside that file's changed-line
  ranges (every line, for a file with no base version). The line is vulture's own.

Neither gate is count-ratcheted and neither reads `.harness-baseline`: there is no
floor to beat, only a before and an after. A pre-existing CCN-30 function this change
did not touch is not this change's problem; the same function at CCN 31 is.

## Definition of done

- `uv run harness check` passes clean — never stop with check failing.
- The stop hook is the agent's feedback loop, not a linter: it blocks with exit 2 and puts the findings on stderr. Read them and fix them; do not re-run the command to see what failed.
- Complexity and dead code are judged as a delta at stop time. Fix what your change made worse; leave the rest of the tree's standing violations to the count-ratcheted gates in `check`/`ci` and the `ratchet` skill.
- User-visible behavior change → a `.feature` scenario exists and acceptance passes.
- No new suppressions: additions above `.harness-baseline` fail check; suppress only with the human's sign-off, stating why.
- Arch config changes are integration-blocked: `check`/`stop-hook` warn, and `pre-commit`/`pre-push`/`ci` fail unless `HARNESS_ALLOW_ARCH_CONFIG=1` is set after review.
- AGENTS.md/CLAUDE.md drift is opt-out-able: retrofitting into a repo with its own AGENTS.md sets `HARNESS_ALLOW_AGENTS_MD_DRIFT=1` rather than overwriting it, and `sync-agents-md` refuses the overwrite anyway.
- Gherkin-first is integration-blocked too: `check`/`stop-hook` warn, and `pre-commit`/`pre-push`/`ci` fail on a changed production-source file (`src/`) with no changed `.feature`, unless `HARNESS_ALLOW_NO_FEATURE=1` is set after review — same shape as the arch config guard. Skipped entirely (passes) when the template has no `.feature` files yet.
- `pre-push`/`ci` are the human's gates: leave the tree in a state where they would pass, but do not commit or push yourself.

## Behavior contract

<important>
## Role

- The human is the engineer. They own design, API shape, and merge authority. You propose, they dispose.
- Do NOT run `git commit`, `git push`, or equivalent publishing commands unless the user's current prompt asked for it. The verbs `commit`, `push`, `ship`, `land`, `merge` in action context authorize that turn only.
</important>

<important if="the task changes user-visible behavior">
- Workflow: write or extend a `.feature` scenario → get human approval → write step definitions → write implementation.
- This is mechanically enforced by `gherkin-guard` (see Commands): a changed `src/` file with no changed `.feature` blocks pre-commit/pre-push/CI unless `HARNESS_ALLOW_NO_FEATURE=1` is set after review.
- If the behavior is law-like (formula, parser, codec, round-trip, invariant), also write a Hypothesis property test, not just examples — see `tests/test_properties.py` for the pattern.
- Refactors, typo fixes, dependency bumps, and internal cleanup are NOT user-visible behavior changes. You MAY proceed without a new `.feature`, but you MUST state in your first response that the change is non-behavioral and why.
- If it is unclear whether a task changes user-visible behavior, ASK before editing source.
</important>

<important if="you want to edit `.importlinter` (arch config)">
- Do not silently edit the arch config to silence a violation. Architectural violations imply a design decision — surface them to the human.
- The harness warns about `.importlinter` changes during `check`/`stop-hook` and blocks `pre-commit`/`pre-push`/`ci` unless `HARNESS_ALLOW_ARCH_CONFIG=1` is set after review.
</important>
